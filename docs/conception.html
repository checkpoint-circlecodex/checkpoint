§1

Le projet en une phrase

Ce qu'on construit, et surtout ce qu'on ne construit pas.

Une application de bureau qui lit un dépôt GitHub privé et en tire une bibliothèque de jeux commune, alimentée au fil de l'eau par un petit groupe d'amis, avec les vues qui rendent la comparaison agréable.

Le tracker solo existe déjà — Backloggd, Grouvee, Steam lui-même. La valeur ajoutée est entièrement collective : savoir qui a fini quoi, sur quoi on n'est pas d'accord, ce qu'un ami a adoré et qui traîne dans ta liste d'envies. Toute fonctionnalité qui ne sert pas ça est du poids mort.

Le binaire est distribuable : on l'envoie à quelqu'un, il l'installe, il demande à rejoindre le groupe, un administrateur valide. L'application est ouverte, ce sont les données qui sont fermées. Cible : une vingtaine de personnes — assez pour que la comparaison soit intéressante, assez peu pour qu'aucune modération lourde ne soit nécessaire.

Ce n'est pas un réseau social, pas un service, pas un produit. L'administration se limite à accepter des gens et, plus tard, à faire le ménage dans le catalogue.

§2

Forme de l'application nouveau v2

Une application installée, pas une page web. Et pourquoi la distinction n'est pas celle qu'on croit.

« Application HTML » recouvre deux choses très différentes. Ce qui est écarté : un fichier qu'on double-clique — pas d'installation, pas d'accès au disque, coincé par les règles du navigateur, aucune présence dans le dock. Ce qui est retenu : une application installée dont la couche de rendu est du HTML et du CSS — ce que sont VS Code, Figma, Linear ou Obsidian.

Il faut l'assumer clairement : avec Tauri, l'interface reste écrite en HTML et CSS. Ce n'est pas là que se joue la différence. Elle se joue ici :

Ce que la coque native débloqueCe que ça change pour ce projet
Plus aucune contrainte CORSLes requêtes partent du code natif, pas du navigateur
Le device flow GitHub redevient possibleL'onboarding passe de six écrans à trois. Plus aucun jeton à copier-coller
Trousseau du systèmeLe jeton va dans le Keychain ou le Credential Manager, plus dans le navigateur
Vrai système de fichiersCache local, mode hors ligne quasi gratuit, export réel
N'importe quelle APIY compris IGDB, qui exige un secret et était hors de portée
Installateurs et mise à jour automatique.dmg, .msi, .AppImage

Le device flow justifie à lui seul le changement : il supprime le point le plus fragile de toute la conception, celui où l'on risquait de perdre un ami à l'étape 4.

Le coût, sans le maquiller

  • Signature de code. Sans compte développeur Apple (99 $/an), le premier lancement affichera un avertissement Gatekeeper, contournable par un clic droit → Ouvrir. Windows affichera un avertissement SmartScreen sans certificat. Acceptable entre amis, à condition de le dire d'avance.
  • Compilation par plateforme. Trois binaires à produire. GitHub Actions le fait gratuitement, sur les trois OS.
  • Chaîne Rust. Nécessaire pour compiler. La part native du projet reste petite — quelques commandes exposées au frontend.
La porte mobile reste ouverte

Tauri 2 vise aussi Android et iOS. Le choix du bureau aujourd'hui ne ferme rien : le jour venu, il faudra une passe d'ergonomie tactile sur la couche du haut, pas un autre projet. C'était le seul argument sérieux en faveur de Flutter, et il tombe.

Le vrai risque

Ce n'est pas la fuite de données — un cercle d'amis, des notes sur des jeux. C'est la corruption ou l'effacement accidentel. Tout le reste de l'architecture découle de ce constat, à commencer par le choix de GitHub.

§4

Décisions actées révisé v16

Les choix structurants. Revenir en arrière coûtera cher ; les tenir ne coûte rien.

⚠️ D9 à D25 ne figurent pas ici mais dans le journal de bord (docs/ETAT.md) : ce sont des décisions d'interface et de lexique, qui relèvent du prototype. Ce document ne porte que celles qui engagent l'architecture ou le modèle.

D1

Les données vivent dans un dépôt GitHub privé

Pourquoi
Chaque écriture est un commit. Face au vrai risque — la corruption — n'importe quelle bêtise se répare en une commande. Drive écrase, Git conserve.
En prime
Détection de conflit native via le SHA du fichier.
D2

Le dépôt appartient à une organisation, pas à un compte personnel

Pourquoi
Les permissions par dépôt — jetons fine-grained comme GitHub Apps — se déclarent au niveau d'une organisation. Sur un dépôt personnel, un ami collaborateur devrait passer par un jeton donnant accès à tous ses dépôts.
Conséquence
Créer une organisation GitHub gratuite, y placer tracker-data en privé.
D3

Jeux vidéo aujourd'hui, modèle extensible aux films

Conséquence
Un champ mediaType présent dès le départ, et progress: { unit, value } plutôt que hours. Une seule machine à états, un vocabulaire différent par média : « Fini » pour un jeu, « Vu » pour un film, « Terminée » pour une série.
Mise à jour v5
Films et séries entrent dès la V1, pas en V3. La décision tient sa promesse : le champ existait déjà, il n'y a aucune migration à écrire. C'est exactement le cas pour lequel il avait été posé.
D4

Données privées — une authentification est requise même pour lire

Pourquoi
Personne n'a à réfléchir à ce qu'il écrit dans ses notes. C'est ce qui rend l'outil honnête.
Conséquence
L'application s'ouvre sur un écran de connexion. Pas de vitrine publique.
D5

Application de bureau en Tauri, interface en React et TypeScript nouveau v2

Pourquoi
Une vraie application installée sur les trois OS, un binaire d'une dizaine de méga-octets, et surtout la fin des contraintes du navigateur — voir §2.
TypeScript
Ce n'est pas un détail de confort : le typage est le mécanisme qui empêche l'ajout d'un bloc de casser un autre en silence. C'est une pièce de C7, pas une préférence.
Repli
Electron, si la chaîne Rust devient un obstacle. Même architecture, même code d'interface ; on n'y perd que la taille du binaire.
D6

Trois couches, dépendances à sens unique nouveau v2

Pourquoi
Permettre d'ajouter une fonction sans toucher aux autres, sans pour autant tout isoler au point de dupliquer. Détail en §6.
Conséquence
Le sens des dépendances est vérifié par une règle de lint, pas par la discipline. Une violation fait échouer la compilation.
D7

L'adhésion se demande depuis l'application ; les droits sont ceux de GitHub nouveau v3

Pourquoi
L'application étant distribuable, il faut un chemin d'entrée pour quelqu'un qui ne connaît personne dans l'organisation. Et il faut qu'un humain décide.
Mécanisme
La demande ouvre une issue sur le dépôt de code public — n'importe quel compte GitHub peut le faire. Un administrateur la voit et valide depuis l'application, ce qui appelle l'API d'adhésion à l'organisation et referme l'issue.
Qui est admin
Les rôles GitHub, pas une liste maison. Est administrateur qui possède ce rôle dans l'organisation. Une liste dans un fichier finirait par diverger des droits réels et créerait une autorité fictive.
Repli
Si l'appel d'API se heurte à une permission, l'application ouvre dans le navigateur une issue pré-remplie. Aucun droit particulier n'est alors requis.
D8

Responsive dès l'origine, pour garder Android ouvert à moindre coût nouveau v4

Pourquoi
Une version Android doit rester une production secondaire : décidée sur un coup de tête, livrée en quelques jours. C'est possible — la plomberie Tauri est bon marché — mais seulement si l'interface n'a pas à être refaite.
Ce que ça impose
Mobile d'abord sur les primitives de mise en page ; requêtes de conteneur plutôt que de fenêtre ; cibles tactiles d'au moins 44 px partout, y compris sur bureau ; aucune action accessible par le seul survol ; les surfaces du noyau ont une forme étroite déclarée ; chaque vue déclare comment elle dégrade.
Ce que ça coûte
Environ 10 à 15 % d'effort de conception en plus par vue, et l'abandon de quelques dispositions luxueuses qui ne tiendraient qu'en large. À comparer à une réécriture de toutes les vues.
Hors sujet
iOS. Techniquement possible, mais la distribution exige un compte Apple et un passage par TestFlight ou l'App Store. Pas un coup de tête.
D26

Le Greffe — l'autorité se range, elle ne se dissimule pas nouveau v16

La distinction
Deux besoins se ressemblent et ne sont pas le même : ce qui demande une autorité (admettre, écarter, fondre un doublon, passer la charge) et ce qui demande seulement de la discrétion (resynchroniser, lire son fragment brut, régler l'affichage des titres). Les réunir donnerait un panneau où une préférence anodine côtoie une exclusion.
Où
L'autorité dans le Greffe, troisième zone de la barre latérale sous sa propre règle — ni agir, ni parcourir : tenir. La discrétion au pied de sa propre feuille.
Qui le voit
Personne d'autre que ceux qui l'ont. L'entrée n'est pas grisée pour les autres : elle est absente. Le rôle est lu dans l'organisation GitHub (D7), jamais dans une liste maison.
Ce qu'il n'est pas
Pas de modération — ce n'est pas une fonction qu'on refuse, c'est une chose non représentable : on n'a pas accès en écriture au fichier d'un autre. Et rien n'y est en coulisse : tout le monde lit le même dépôt, donc tout acte paraît dans l'historique de chacun. L'écran le dit.
Palier
Le guichet des admissions est V1 — le critère de la V1 est qu'un inconnu entre sans explication, et il n'entre pas si personne ne peut l'admettre. Le reste (doublons, journal, passation) est V2.
D27

Un doublon se fond par un alias déclaré, appliqué à la lecture nouveau v16

Le problème
Deux personnes inscrivent la même œuvre à la main faute de l'avoir trouvée, et le catalogue en porte deux. Corriger imposerait d'éditer leurs fichiers — ce qu'interdit « un seul écrivain par fichier ».
La forme
Le greffier déclare { from, to } dans son propre fragment, et la fusion applique le repli à la lecture. Rien n'est réécrit, rien n'est supprimé, et l'alias se retire — la seule garantie qui tienne quand on s'est trompé.
Cas limite
Si une même personne tenait les deux entrées, la fusion n'en garde qu'une : la plus récente.
Portée
C'est la même grammaire que les favoris, les surlignages et les quêtes : une déclaration rangée chez soi, sommée à la lecture. Tout fait collectif à venir prendra cette forme — c'est ce qu'impose le modèle, pas un choix de style.
§5

Architecture des données

Un fichier par personne — la décision qui empêche le projet de se casser en silence.

Plutôt qu'une base partagée, chaque participant possède son fichier et n'écrit que dedans. L'application lit les N fichiers et les fusionne à l'affichage.

tracker-data/ dépôt privé, organisation ├── data/ │ ├── nathan.json seul Nathan y écrit │ ├── alice.json seule Alice y écrit │ └── bob.json └── meta/ └── members.json liste des participants — rare, édité à la main

Ce que ça donne gratuitement :

  • Zéro conflit d'écriture, par construction. Pas de verrou, pas de fusion à trois voies, pas de perte silencieuse.
  • Rayon de dégât limité. Un fichier corrompu n'emporte pas les autres.
  • Le catalogue devient dérivé. Un jeu existe parce qu'au moins une personne le suit — ce qui correspond exactement à l'usage.
  • Ajouter un ami, c'est ajouter un fichier. Aucune migration.
Règle d'or

On ne stocke que des faits, jamais des agrégats. Le catalogue, les moyennes, les classements, les compteurs : tout se recalcule au chargement, à chaque fois. Un agrégat stocké est un agrégat qui devient faux, puis qu'on ne sait plus régénérer. C'est précisément ce qui tue ce genre de projet au sixième mois.

Lire vingt fichiers sans ramer

Un appel à l'arbre Git du dépôt rend en une fois le chemin et le SHA de tous les fichiers. On ne télécharge ensuite que les blobs dont le SHA a bougé depuis la dernière ouverture, les autres sortant du cache local. Une ouverture sans changement coûte une seule requête. À vingt personnes c'est confortable ; à cent ça le resterait.

Le conflit d'écriture, provoqué exprès — 11 octobre 2026 nouveau v16

Écriture acceptée, puis 409 Conflict sur un SHA périmé. Le signal « relis, fusionne, réessaie » existe donc bel et bien — et comme un seul écrivain touche chaque fichier, il ne devrait jamais se déclencher. C'est un filet, pas un mécanisme de fonctionnement : le jour où il se déclenche, c'est qu'un invariant a été enfreint ailleurs.

Verdict : Git reste le bon choix, et rien ne s'en approche sur l'axe qui compte ici — gratuit, sans serveur à administrer, sans compte à gérer, et surtout versionné, donc réparable. La Loge ne remet pas ce choix en cause ; elle ajoute deux règles de client, pas une migration.

Le seuil où la réponse basculerait est précis : le jour où quelqu'un attendra de voir un message apparaître sans rien rafraîchir, ou d'être averti. Et même là, la bonne réponse ne serait pas de déplacer les données :

  • Un canal de réveil qui ne stocke rien. Un relais minuscule — un worker gratuit, un courtier de messages — qui ne transporte qu'un signal « quelque chose a changé ». Les données restent dans Git, aucun invariant ne tombe, et le relais peut mourir sans rien emporter. C'est l'échappatoire à retenir.
  • Pas une base temps réel hébergée (Firebase, Supabase). Elle rendrait le direct, mais réintroduirait exactement ce qu'on a supprimé : un magasin partagé modifiable, donc le conflit d'écriture et la corruption silencieuse. Elle ajouterait un compte à administrer, un propriétaire unique, et des paliers gratuits qui se suspendent. On échangerait un défaut visible contre un défaut invisible.
  • Pas Discord non plus — qu'ils ont déjà, et qui fait mieux le travail de salon. Si la Loge n'était qu'un salon, Discord gagnerait et il faudrait la retirer. Sa raison d'être est d'être attachée à l'Ordre et aux œuvres : on y cite une fiche, on y surligne, on retrouve un passage six mois plus tard. C'est ce que Discord ne fait pas.

Identifier un jeu : le piège discret

Si chacun saisit le titre à la main, « Zelda BOTW » et « Breath of the Wild » deviennent deux jeux distincts et toutes les vues de comparaison s'effondrent. La parade : une recherche sur une base externe au moment de l'ajout, qui rend un identifiant canonique igdb:1020 et la jaquette. Un seul mécanisme règle la déduplication et alimente la beauté visuelle. Saisie manuelle possible en repli, avec un identifiant local:hollow-knight.

La coque native rend IGDB accessible — sa clé secrète voyage dans la partie Rust, jamais dans l'interface. C'est la base la plus complète du domaine ; RAWG reste le repli si l'authentification Twitch qu'elle exige s'avère pénible.

§6

Architecture logicielle nouveau v2

Ajouter sans casser, sans pour autant tout isoler au point de devoir réécrire.

C'est une tension réelle, et les deux moitiés comptent autant. Des blocs parfaitement étanches, c'est du copier-coller partout et une interface qui part dans tous les sens. Des blocs qui se connaissent tous, c'est le retour de l'effet domino. La sortie n'est pas dans le cloisonnement, elle est dans un noyau partagé et un sens de dépendance unique.

R1
Les dépendances vont dans un seul sensFonctions → Noyau → Plateforme. Jamais l'inverse, et jamais entre deux fonctions. Ce n'est pas une convention qu'on oublie : une règle de lint la fait échouer à la compilation.
R2
Un seul modèle de données, un sélecteur par fonctionC'est la règle qui répond à la crainte de réécriture. Si chaque bloc avait sa propre forme de données, en ajouter un obligerait à re-transformer les données partout. Ici toutes lisent le même magasin fusionné : une nouvelle fonction, c'est un sélecteur et une vue. Les autres ne bougent pas d'une ligne.
R3
Un registre de vuesChaque bloc se déclare — identifiant, libellé, icône, composant, et comment il dégrade en étroit. La coque construit la navigation à partir du registre. Ajouter une vue, c'est un dossier et une ligne ; la supprimer, c'est effacer le dossier.
R4
La règle de promotionUn bloc garde ses composants propres chez lui. Dès qu'un deuxième bloc en a besoin, il monte dans le noyau. Pas avant — on ne généralise jamais sur un seul cas — mais jamais deux fois non plus. C'est ce qui évite à la fois le copier-coller et l'abstraction prématurée.

Anatomie d'un bloc

src/ ├── features/ les blocs │ └── matrice/ │ ├── index.ts déclaration au registre — seul point de contact │ ├── MatriceView.tsx │ ├── selectors.ts ce qu'elle tire du noyau │ └── components/ ses composants propres, non partagés ├── core/ le noyau │ ├── model/ schéma, fusion, migrations │ ├── selectors/ sélecteurs partagés │ └── ui/ design system, primitives, surfaces ├── platform/ adaptateurs, derrière une interface │ ├── storage.ts GitHub — ou faux en mémoire, pour la V0 │ ├── secrets.ts trousseau du système │ └── cache.ts └── shell/ navigation construite depuis le registre src-tauri/ la part Rust : HTTP, trousseau, fichiers

Les surfaces, et les « fenêtres intérieures »

Panneaux, superpositions, tiroirs, et les petits effets visuels qui les accompagnent : tout ça vit dans le noyau, comme un vocabulaire partagé. Sans cette règle, chaque bloc réinventerait ses propres panneaux, et l'interface se mettrait à diverger — exactement ce que le soin porté à l'UI cherche à éviter.

Chaque surface a une forme large et une forme étroite, décidées une fois dans le noyau : un panneau latéral devient une feuille du bas, une superposition devient un plein écran. Les blocs n'ont rien à savoir de tout ça — ils demandent une surface, pas une disposition. C'est ce qui fait qu'une version Android n'oblige pas à rouvrir chaque vue.

La plateforme doit rester portable

La couche du bas est la seule dont le code change entre le bureau et Android. Deux adaptateurs sur quatre y sont sensibles : le stockage du secret, et la mise à jour. Les deux se règlent en choisissant maintenant — une implémentation de secret portable plutôt qu'une bibliothèque de trousseau de bureau, et un bandeau de nouvelle version en complément de l'updater. Les deux autres, HTTP et cache fichier, fonctionnent tels quels.

Ce que ça garantit pour la suite

révisé v16 La ligne annonçait un cahier des charges UX/UI qui atterrirait dans la couche du haut. Il n'arrivera pas, et la démonstration a eu lieu sans lui : trois jours de décisions d'interface — Loge, Quêtes, lignée, Greffe, entrée dans le groupe — n'ont touché ni le noyau, ni la plateforme. C'est la preuve que la séparation voulue ici fonctionne, et elle vaut mieux qu'une promesse.

Piège à éviter

L'identifiant est le compte GitHub, jamais le pseudo, et c'est lui qui nomme le fichier. Un pseudo se change ; si le nom du fichier en dépendait, le renommer orphelinerait tout l'historique de la personne.

history mérite une mention à part : c'est lui qui donne gratuitement le fil d'activité — « Alice a fini Hollow Knight il y a deux jours » — et c'est très probablement ce qui fera revenir les gens, plus qu'une grille de jaquettes.

Faire à plusieurs, et refaire nouveau v10

Deux ajouts au modèle d'entrée, tous deux additifs :

  • with[] — les compagnons. Une œuvre achevée à plusieurs porte la liste de ceux avec qui on l'a faite. Les chroniques restent individuelles : chacun écrit la sienne, ou n'écrit pas. Partager l'expérience n'est pas partager le jugement, et confondre les deux aurait fait du groupe un auteur collectif, ce qu'il n'est pas.
  • plays — le compteur de passages. Refaire une œuvre n'est pas une seconde entrée : ce serait dupliquer un fait au lieu de le compter, et toutes les statistiques s'en trouveraient faussées. Un bouton discret sur sa propre ligne incrémente, rien de plus.

Les genres, eux, appartiennent à l'œuvre et non à l'entrée : ils partent dans works, comme la jaquette, et la fusion retient la première contribution. Un tronc commun à toutes les natures — horreur, romance, action… — complété par ce qui n'a de sens que pour l'une d'elles : FPS, roguelite, shoot'em up pour les jeux, essai ou roman graphique pour les livres.

Distinguer : les favoris et le magnum opus nouveau v11

Une section de plus dans le fragment : favorites[], une liste ordonnée d'identifiants d'œuvres, plafonnée à douze.

  • Un favori n'est pas une note. C'est une déclaration d'attachement, pas un jugement : on peut distinguer une œuvre qu'on n'a pas finie, ou en défendre une qu'on a jugée moyenne. La dériver d'un classement de notes reviendrait à n'avoir rien ajouté au modèle. On ne distingue en revanche pas ce qu'on convoite sans l'avoir fréquenté.
  • L'ordre porte du sens. Le premier rang est le magnum opus de la personne. Le plafond de douze n'est pas une limite technique : au-delà, une liste de favoris redevient un second registre et cesse de choisir.
  • L'Ordre en tire un étendard. L'onglet Magnum opus d'une chambre somme les distinctions de ses membres : ce qui réunit le plus de voix passe devant, à égalité le rang que ses tenants lui donnent tranche. C'est le seul accord de l'application qui se déclare au lieu d'être calculé — tout le reste se déduit des notes. Quand aucune œuvre ne réunit deux voix, l'écran le dit plutôt que de feindre l'unanimité.

La lignée : un lien qui traverse les Ordres nouveau v15

Une section de plus : kin[], où chacun déclare ce que les autres sont pour lui — { id, rel }, rel parmi père, mère, parent, fils, fille, enfant, frère, sœur, fratrie.

  • Un lien n'existe que déclaré des deux côtés, et les deux déclarations doivent s'accorder en sens : « mon fils » appelle « mon père », « ma sœur » appelle « mon frère ». C'est ce qui interdit de s'inventer une famille, et ça ne demande aucun mécanisme d'invitation : l'invariant premier suffit.
  • La maisonnée n'est pas un objet qu'on possède : c'est la composante connexe des liens confirmés. Personne ne la crée, personne ne la détient, elle apparaît — et elle se recalcule comme tout le reste.
  • Le mot est toujours celui de l'autre. C'est l'enfant qui dit « mon père », donc l'écran écrit « père de ». Personne ne se nomme soi-même dans une famille, et ça évite d'inventer un champ de genre dont on n'a pas besoin.
  • C'est le premier lien de l'application qui traverse les Ordres. On choisit son Ordre ; on ne choisit pas sa maisonnée. Conséquence d'interface : le point d'entrée doit être neutre, sans quoi il faudrait choisir la teinte d'un membre contre celle des autres.

C'est le quatrième fait collectif du modèle, et il a la forme des trois autres : rien n'est déclaré en commun, tout est sommé à la lecture. À ce stade ce n'est plus une coïncidence — c'est la grammaire qu'impose « un seul écrivain par fichier », et toute fonction collective à venir la prendra aussi.

Les quêtes : des paliers, pas des trophées nouveau v13

Une section de plus : quests[]. Une quête porte un nom, une ligne, et des épreuves — chacune un palier à atteindre sur un groupe d'œuvres. « Avoir achevé le Silmarillion, la trilogie et le Hobbit » est une épreuve ; « avoir entrepris Silent Hill 1 à 4 » en est une autre.

  • Nul ne valide une quête : elle s'accomplit d'elle-même. Qui l'a accomplie se recalcule à chaque lecture, comme tout agrégat — rien n'est jamais écrit. C'est ce qui la sépare d'un trophée décerné : il n'y a personne à convaincre, donc rien à administrer.
  • Les paliers sont monotones, et c'est ce qui fonde tout le reste : convoiter < entreprendre < achever. Avoir renoncé ou accompli, c'est avoir entrepris ; accompli vaut achevé. Une fois atteint, un palier ne se reperd pas.
  • Ce qui en découle, et qu'il faut refuser : « suspendu » ne peut pas être un palier, puisqu'on en sort. Une quête qui se désaccomplirait parce que quelqu'un a changé un statut serait cruelle, et elle rendrait l'onglet d'un Ordre instable. Si un palier non monotone est demandé un jour, c'est là qu'il faut s'arrêter et en parler.
  • Une quête vit dans le fragment de qui l'ouvre. Elle est donc visible de tous, et seul son auteur peut l'arracher — même règle que la Loge, même invariant.

Elles paraissent à trois endroits : une section propre, un volet sur la feuille de chacun (ce qu'il a accompli), et un volet dans la chambre d'un Ordre — avec le décompte de ceux des siens qui l'ont menée au bout. C'est le troisième fait collectif du modèle, et il a la même forme que les deux autres : rien n'est déclaré en commun, tout est sommé à la lecture.

La Grande Loge : un fil fermé par Ordre révisé v12

Deux sections : loge[], les messages de la personne — order, at, body, et au besoin ref (une œuvre citée) et replyTo (sans arborescence) — et marks[], les identifiants des messages qu'elle a surlignés. La fusion rassemble les deux ; la chambre d'un Ordre affiche le fil dans le sens du temps, dense, avec son propre défilement, ouvert sur son présent.

  • On n'entre dans une Loge que si on est de l'Ordre. Les autres trouvent porte close : « Vous ne faites pas partie de la grande loge. Ses secrets vous sont interdits. » — le seul vouvoiement de l'application, parce que la porte ne vous connaît pas. ⚠️ C'est une règle d'usage, pas une clôture : tout le monde lit le même dépôt privé, donc l'application fait respecter la convention et ne garantit pas le secret. Ne jamais laisser croire le contraire. Une vraie clôture demanderait un dépôt par Ordre avec des équipes GitHub, ce qui briserait « un fichier par personne » — le prix est trop élevé pour ce qu'on y gagne.
  • Surligner est une marque personnelle rangée chez soi. Un message est surligné dès qu'une personne l'a marqué ; le compte dit combien ; on ne retire que la sienne. Replié, le fil ne garde que les surlignés — un index construit à la main par ceux qui lisent — et rouvrir un passage ramène à l'endroit exact d'où il vient.
  • Les faits collectifs de l'application sont tous de la même forme : le magnum opus d'un Ordre, les surlignages d'un fil, le décompte d'une quête, la maisonnée — des déclarations rangées chez soi et sommées à la lecture. C'est la forme qu'impose « un seul écrivain par fichier », et tout fait collectif à venir la prendra aussi.

Cela révise le hors-périmètre de §11, qui excluait « commentaires et fils de discussion ». Ce qui les excluait réellement, c'était le conflit d'écriture et la modération. Or :

  • Le conflit d'écriture n'existe pas : chacun n'écrit que dans son propre fragment. L'invariant premier tient sans une ligne de code en plus.
  • La modération n'est pas une fonction refusée, elle est non représentable : on n'a pas accès en écriture au fichier d'un autre, donc nul n'efface le message d'autrui. Chacun retire les siens.
  • Un message reste dans l'Ordre où il a été dit, même si son auteur en change : d'où le champ order, qui n'est pas une redite de la classe de la personne.
  • Écrire se groupe. Un fil bavard ne produit pas un commit par message : le client accumule et écrit après quelques secondes d'inactivité. L'historique du dépôt est ce qui rend les données réparables — le noyer sous des commits d'une ligne, c'est perdre la propriété qui a fait choisir Git.

Le prix se paie dans l'interface, pas dans le modèle : sans serveur, aucun message n'est poussé. Il paraît chez les autres à leur synchronisation suivante et personne n'est averti. L'écran l'écrit en toutes lettres — même honnêteté que l'écran d'attente d'adhésion. Ce qui reste hors périmètre : les fils arborescents, et les commentaires attachés à une œuvre — la chronique est le seul écrit qu'une œuvre porte.

Les checkpoints, et pourquoi ce n'est pas une chronique révisé v9

Un checkpoint est une pensée datée, prise pendant qu'on avance, qui ne prétend à aucun verdict. Le contenu signature de l'application porte son nom : un point de sauvegarde sur le trajet. Une chronique est un jugement rédigé après coup, avec un titre qui le résume. Les confondre serait une erreur de modèle autant que de ton : l'une se consigne à la volée depuis la feuille de personnage, l'autre se compose.

Suspendu n'est pas Renoncé. Le volet « En cours » d'une feuille ne montre que playing ; mettre une œuvre de côté la fait descendre au registre sans verdict, et ce geste doit rester à un seul clic — c'est le plus fréquent de tous.

Titre original, titre français révisé v7

Une même œuvre circule sous plusieurs noms, et chacun connaît le sien. Le problème est moins grave qu'il n'y paraît, parce qu'il est déjà résolu à moitié par l'identité : deux personnes qui portent « Past Lives » et « Nos vies d'avant » depuis la source tombent sur le même tmdb:, donc sur la même fiche. Le titre n'a jamais été l'identité.

Reste l'affichage, qui se règle en trois points :

  • L'œuvre porte les deux titres — title pour la version originale, titleFr quand elle diffère. Tous deux viennent de la source.
  • Le choix est une préférence de personne, rangée dans son propre fragment (user.prefs.titles), donc transportée d'une machine à l'autre. Ce n'est pas un réglage de vue : c'est un fait sur quelqu'un.
  • La recherche interroge toujours les deux, quelle que soit la préférence. C'est le point qui compte le plus — sans lui, on ne retrouve jamais une œuvre sous le nom qu'on lui connaît. La fiche affiche l'autre titre sous le principal, pour que personne ne reste perdu.

Le cas qui reste ouvert est celui de la saisie manuelle : deux personnes décrivant la même œuvre à la main produisent deux identifiants local: distincts, donc un vrai doublon. C'est précisément pourquoi la recherche dans le fonds est le chemin par défaut et la description manuelle l'exception — et pourquoi l'onglet d'administration de la V2 sait fusionner.

Les jaquettes, et pourquoi Git ne pardonne pas révisé v6

Une jaquette peut être importée à la main quand aucune source ne la fournit. Le redimensionner avant écriture est nécessaire, mais ce n'est pas la vraie contrainte : dans un dépôt Git, un fichier remplacé n'est jamais effacé. Chaque version d'une image reste dans l'historique, pour toujours, et chaque personne du groupe la retélécharge à chaque clone. Un dépôt de données qui accueille des binaires grossit sans jamais pouvoir maigrir.

CasTraitement
Jaquette issue d'une base externeOn stocke l'URL, jamais les octets. C'est le cas par défaut, et il ne coûte rien au dépôt.
Aucune jaquette disponibleLe cadre porte le titre de l'œuvre, composé. Aucune image, aucun poids.
Jaquette importée à la mainRedimensionnement côté natif avant écriture — plafond à fixer, de l'ordre de 400 × 600 et 60 ko en WebP. Et un garde-fou : refuser l'import au-delà du plafond plutôt que de le contourner.

À trancher dans le cahier des charges : si les imports manuels deviennent fréquents, les images doivent quitter le dépôt de données pour un dépôt séparé, qu'on peut réinitialiser sans perdre les faits.

§8

Entrer dans le groupe révisé v3

Le parcours détaillé vit dans le document de parcours. Ici, seulement ce qui a des conséquences techniques.

L'application se distribue librement : quelqu'un peut l'installer sans connaître personne. Il faut donc un chemin d'entrée pour un inconnu, et un humain qui décide au bout. Quatre étapes.

  1. Compte GitHubSe connecter, ou en créer un. Le device flow affiche un code court ; la personne l'autorise sur github.com et revient. Le jeton part directement dans le trousseau du système. Aucun jeton à copier-coller.
  2. Demande d'adhésionL'application ouvre une issue sur le dépôt de code public, avec un corps structuré. N'importe quel compte GitHub peut le faire — c'est ce qui rend le parcours possible pour un inconnu.
  3. Validation par un administrateurUn administrateur voit la demande dans l'application et l'accepte : appel à l'API d'adhésion à l'organisation, puis fermeture de l'issue. Est administrateur qui possède ce rôle dans l'organisation GitHub — pas de liste maison.
  4. ProfilPrénom, pseudo, classe, couleur, Discord en optionnel. Création de data/<compte-github>.json. L'application est utilisable.
Entre l'étape 2 et l'étape 3, il ne se passe rien

Et c'est le seul vrai risque du parcours. Sans serveur, aucune notification n'est possible : ni pour prévenir l'administrateur qu'une demande arrive, ni pour prévenir le demandeur qu'elle est acceptée. L'écran d'attente doit le dire franchement, vérifier à chaque ouverture, et proposer une relance par Discord. C'est la raison d'être du champ Discord, et non un ornement.

Confirmé par le spike — 11 octobre 2026 révisé v16

Les deux points en suspens sont tranchés, et mesurés contre la vraie API. Le device flow passe depuis la coque : jeton obtenu sans copier-coller. Il n'expire pas — la case Expire user authorization tokens a été laissée décochée sur la GitHub App, donc il n'y a aucun renouvellement à écrire. Une issue s'ouvre bien sur le dépôt public : c'est le seul geste d'un extérieur, et il suffit. Et l'API d'adhésion répond (rôle « admin », état « active »), ce qui fonde le guichet du Greffe (D26). Les replis restent écrits mais ne servent plus : issue pré-remplie dans le navigateur, jeton fine-grained collé à la main. Un 401 rejoue l'étape de connexion seule, jamais le parcours entier.

§10

Trajectoire révisé v3

Un point de passage obligé, puis quatre paliers.

Avant toute interface

Une coque Tauri nue qui prouve quatre choses, dans l'ordre : le device flow aboutit à un jeton exploitable ; la lecture de data/*.json dans un dépôt privé fonctionne ; l'écriture rend un SHA ; et une réécriture avec un SHA périmé rend bien un 409. Ce dernier point est l'hypothèse sur laquelle repose toute la détection de conflit — c'est le seul endroit du projet qui peut le tuer. Tant qu'il n'est pas validé, aucune interface.

Les trois couches en place, le registre de vues, la règle de lint, un faux stockage en mémoire. Bibliothèque et fiche jeu. Valider l'ossature et l'ergonomie pendant que ça ne coûte encore rien de tout jeter.

§11

Hors périmètre révisé v11

Écrit noir sur blanc maintenant, c'est ce qui gardera le projet élégant dans six mois.

  • Temps réel et présence — exige un serveur.
  • Commentaires et fils de discussion — le groupe a déjà une conversation ailleurs. Révisé en v11 : la Grande Loge — un message board par Ordre — entre au périmètre, parce que ce qui l'excluait (conflit d'écriture, modération) ne s'applique pas à un modèle où chacun n'écrit que chez lui. Voir §7. Restent exclus : les fils arborescents, et les commentaires attachés à une œuvre — la chronique est le seul écrit qu'une œuvre porte.
  • Notifications push — exige un serveur. Conséquence assumée : voir §8.
  • Comptes et mots de passe maison — c'est exactement ce que GitHub nous évite.
  • Import Steam automatique et succès — exige un serveur pour tenir les jetons dans la durée. Reporté sans date.
  • Administration lourde — un onglet en V2 pour fusionner des doublons et gérer les membres, pas un back-office. À vingt personnes, ça suffit largement.
  • Version mobile — reportée, pas exclue : Tauri 2 la rendra possible sans changer de projet.
